# Frontend foundation and identity

Browser → Supabase Auth (session and identity); browser → Fastify `/api/v1/me` (application profile); Fastify → PostgreSQL. Front never queries database tables directly.

- `app`: constructs one Auth controller, API client and QueryClient per application; provides them to React.
- `auth`: one official Supabase AuthClient singleton, bounded requests, PKCE callbacks, session store and public forms. The client uses explicit localStorage, the SDK-compatible project storageKey, `flowType: 'pkce'`, `skipAutoInitialize: true`, and `detectSessionInUrl: false`. `createClient()` cannot guarantee callback exchange first in supabase-js 2.117.2 because its internal listener reads storage in the constructor. On a code callback, the gateway alone exchanges through a cached promise before initialization or listener registration; it removes the code after the returned session, then initializes and checks getSession. Ordinary routes initialize before reading session. StrictMode does not exchange twice. A valid recovery exchange establishes recovery context without requiring an event. The SDK listener registers after bootstrap and replays events; controller subscriptions clean up on unmount without removing verifiers. Requests check verifier persistence; pending recovery blocks app logout. SDK security cleanup remains intact, with temporary sanitized localhost diagnostics. Stale initialization results cannot overwrite a later Auth event.
- `routing` / `layouts`: loading is distinct from signed-out state. Recovery sessions stay in the recovery flow. Public and authenticated layouts share accessible primitives.
- `api` / `profile`: current Bearer token in memory, safe errors and Zod response validation matching the backend's camelCase contract. A 401 invalidates only the session that issued that request. Private cache clears on identity changes/logout; a late profile mutation cannot restore another session's data.
- `components/ui`: locally owned shadcn/ui-style Button (Radix Slot + CVA), Input, Label and Card, manually integrated following the official installation pattern. `components.json`, aliases and Tailwind tokens support further shadcn additions. Only needed primitives exist.

Forms use React Hook Form and Zod. Input errors are linked by `aria-describedby`; loading, failure and success use live semantics. The layout supports 320px upwards, visible keyboard focus and reduced motion. Warm neutral surfaces, evergreen accents and restrained editorial headings establish the initial visual language.

Supabase controls token storage/refresh; there is no application-managed JWT persistence. Profile fields never include an owner. Metadata is not authorization. Provider messages, JWTs and passwords are never logged. Browser configuration accepts only public key and safe URL origins. App data endpoints are not replaced with browser database access.

Dependencies are pinned in the lockfile. TypeScript 6 is retained for compatibility with typescript-eslint's supported peer range; jsdom 26 supports the project's Node 24 baseline. Official references: [Supabase PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow), [password recovery](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail), [shadcn manual installation](https://ui.shadcn.com/docs/installation/manual).

Tests: unit boundaries and session races; React integration with mocked external boundaries; Chromium desktop/mobile using the real browser SDK against intercepted Auth/API responses. Real remote checks and remaining human e-mail actions must be reported separately in PROJECT_STATE. No backend/schema migration or MDL 2 feature is introduced.

## Clean-room Auth preview (pending real gates)

`src/auth-v2/` is independent of the historical `src/auth/` controllers, gateways, callbacks, and diagnostics. The default Vite mode still mounts the historical app; `vite --mode auth-v2` mounts the new preview without deleting or cutting over the old implementation. Both use the existing public Supabase URL and publishable key, never a browser service-role key.

The preview has one default `createClient` singleton and one application-lifetime `onAuthStateChange` subscription. The SDK supplies the initial session and persistence; the app holds no separate JWT storage. Login uses `signInWithPassword`, signup uses `signUp` with a same-origin confirmation redirect, and recovery requests use `resetPasswordForEmail` with a same-origin recovery redirect. The two callback routes use a single `verifyOtp` call with `token_hash` (`email` for signup, `recovery` for password reset), then remove the hash from the URL. Only a verified recovery session can call `updateUser({ password })`.

Protected routes distinguish loading, authenticated, and unauthenticated states. Their profile preview reads only `GET /api/v1/me` using the SDK session's access token and validates the response owner; the Back does not expose a separate `GET /api/v1/me/profile`. The preview is not a replacement for the full profile editor. Local automated tests use intercepted Auth/API traffic; they do not prove remote email delivery or real login. Configure remote email templates and perform real login, signup, and recovery gates separately and sequentially before any cutover.
